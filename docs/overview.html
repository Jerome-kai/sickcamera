Fork of openai/imagegencam — ported to the parts I already had

A camera that redraws every photo it takes.

Press the shutter, the viewfinder freezes for a beat, and an image model repaints the frame in whatever style is loaded. The upstream project wants a Raspberry Pi Zero 2 W and a Pimoroni HAT. This one runs the same camera on an Orange Pi Zero 2, a 3.5" SPI panel, a USB webcam board and five keyboard switches — talking to any OpenAI-compatible gateway.

Bill of materials — every substitution

The swap

Nothing here is a like-for-like part. Each swap changed something in software: a new panel driver, a GPIO shim, a V4L2 capture path, a gateway-agnostic API client.

Orange Pi Zero 2 Allwinner H616
Raspberry Pi Zero 2 W

Different SoC, different GPIO numbering: lines are port × 32 + pin, so PC9 is line 73. Two backends sit behind one interface — libgpiod, plus a sysfs path for the stock 4.9 kernel image.

3.5" ST7796U IPS 480×320
Pimoroni Display HAT Mini (ST7789, 320×240)

A new panel driver, st7796.py, pushes RGB565 over spidev with DC/RST/backlight on three gpiod lines. Whole frames go out in a single writebytes2 call. ILI9341 240×320 modules also work.

USB UVC board camera V4L2
CSI spy camera for Pi Zero

OpenCV replaces picamera2 — and the service now waits for the device to enumerate instead of dying on a slow udev at boot.

5 mechanical switches 1 MX + 4 tactile
HAT buttons + PiSugar shutter

The shutter is a full keyboard switch, unmistakable by feel. The four UI switches sit on a perfboard strip behind the front panel, pulled up in software — no resistors.

18650 pack, 2800 mAh 5 V / 3 A
PiSugar 3

A generic charge/protect/boost PCB with USB-C in and a JST lead out. No battery telemetry over I²C, and no soft power switch yet — which is the first item on the V2 roadmap.

Any OpenAI-compatible gateway OPENAI_BASE_URL
OpenAI API, direct

Three request shapes are supported — edits, chat and generations — so gateways without /v1/images/edits still work.

The signal path

Generation happens in the background, so the camera keeps shooting while it works. Jobs are small JSON files, not an in-memory queue — pull the battery mid-generation and the work resumes on the next boot.

One service. The controller owns the hardware loop and never blocks on the network; the web server is a separate surface on the same process, local-LAN only by design.

V2 — measure before rewriting, fix causes not symptoms

Known defects

V1 works. It also boots for five minutes, hangs together on dupont wires, and greets a new owner with a published hotspot password. V2 treats those as defects rather than quirks.

01 · Power

The switch is the bug. It sits in the power line, so every “off” is a hard cut and every “on” is a cold boot of Ubuntu, the service, Wi-Fi association and camera enumeration.

Fix: a MOSFET soft-latch with sense and hold lines, and a real sleep state — backlight off, camera released, wake on the shutter. A rewrite in a faster language is explicitly rejected: the app already starts in seconds.

02 · Carrier PCB

Dupont wires and a perfboard strip do not survive being carried around.

Fix: one small board that carries the header, the switches, the latch circuit and the panel connector — scoped to a first PCB that can actually succeed.

03 · UX

The camera is usable by the person who built it, which is not the same as usable.

Fix: first-run tutorial, screen sleep and clearer state on the panel — some of this has already landed.

04 · Security

Stop publishing the keys. A shared hotspot password and a wide-open local web app are fine on a bench and wrong on a device you hand to someone.

Fix: per-device credentials (done), a narrow sudoers rule for the few nmcli commands (done), and authentication on the phone app before it goes anywhere but the LAN.
